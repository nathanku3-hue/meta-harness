Execution Frontier needs one important decomposition.

Model the corporation; don’t simulate the corporation.

I’d sharpen that to: model intent, authority, capability, state, and commitments; instantiate agents only at the execution edge.

The interesting convergence in the newest work is toward exactly that shape. The August 9, 2026 Fluid Structure, Rigid Record paper explicitly argues that an agentic organization should not be model instances wearing corporate titles; it separates persistent records/authority from dynamically assembled task groups and narrow execution leases. But it is still an independent draft with only prototype/small-sample validation, so I’d treat it as strong architectural convergence, not empirical proof.

What I think you're missing

Split Frontier eligibility from allocation/admission.
“These three lanes are runnable” is not the same decision as “run lanes A and C now.” Kubernetes/Kueue has unusually good semantics to steal here: controllers continuously reconcile desired and observed state, while Kueue separately reserves quota, runs admission checks, and only then admits work; it also has priority, preemption, and historical fair sharing.

So I would make:
World → Candidate → Eligible → Admitted → Leased → Executing, rather than Frontier → worker.

Add reconciliation as a first-class architectural principle.
CMMN gets you evolving case semantics, but Kubernetes provides the implementation pattern I'd steal: preserve desired intent independently of observed state and continuously derive what must/can happen next. A Frontier then becomes a derived read model, not mutable planning state.

Add an explicit proposal/commit boundary.
This is probably the biggest missing piece. The 2026 Organizational Control Layer research separates what an LLM proposes from what the environment actually executes; an external layer can approve, rewrite, block, or escalate. Their narrow adversarial negotiation evaluation reports unsafe executions falling from 88% to near-zero and valid success rising from 12% to 96%, though that result should not be generalized beyond the experiment. Source code is published.

In Meta-Harness terms: workers do not mutate World. Workers produce proposed effects. A deterministic control plane commits effects.

Your Role/Post/Authorization split needs two more identities.
I would explicitly distinguish organizational role, runtime agent identity, delegated authority, and principal/on-whose-behalf. OMG Commons 1.3 now has an explicit Business Authorizations ontology, while W3C PROV models delegation/actedOnBehalfOf and retained responsibility.

OpenFGA's brand-new task-based agent authorization guidance is almost uncannily aligned: task-scoped permissions, expiry, maximum invocation counts, runtime contextual grants, binding an agent to a task, and narrower re-delegation to subagents.

Add provenance/accountability as distinct from authorization.
Authorization answers may this effect happen? Provenance answers who caused this, acting for whom, based on what evidence? W3C PROV already supplies useful semantics here, including activity-specific delegation.

Every committed effect should therefore carry something like actor_instance, principal, role/post, authorization/lease, decision, evidence, policy_version, and causal_parent.

Add BMM + BACM ahead of UAF in your core ontology.
I'd keep UAF for enterprise views/traceability, but BMM + BACM are closer to the Meta-Harness domain core. OMG explicitly positions BMM and BACM in its business-architecture stack, with BACM centered on business capabilities; BACM has a formal 1.0 and a 1.1 beta. Current revision work is also wrestling with outcomes around value-stream/capability execution.

Roughly: ISO 37000 → governance constitution, BMM → durable motivation, BACM → capability/value structure, CMMN → changing operational situation.

Formally specify Frontier invariants before making it clever.
This is fundamentally a concurrent authorization/resource-allocation machine. TLA+/TLC is a better investment here than another reasoning-agent layer. In particular I would model-check revocation, concurrent admission, leases, stale world state, retries, and competing resource claims.
The hardened Execution Frontier

I would define it closer to this:

AuthoritativeState =
    Intent
  × WorldFacts
  × Organization
  × Policies
  × Resources
  × Evidence

Candidates = propose_work(AuthoritativeState)

Frontier = {
    c ∈ Candidates |
      preconditions(c)
      ∧ dependencies_satisfied(c)
      ∧ evidence_sufficient(c)
      ∧ policy_eligible(c)
}

Admitted = allocate(
    Frontier,
    budgets,
    scarce_capabilities,
    concurrency_limits,
    conflicts,
    priorities,
    fairness,
    risk
)

Lease = authorize(
    admitted_work,
    executor,
    tools,
    resources,
    budget,
    expiry,
    policy_version
)

Proposal = execute(Lease)

Commit =
    validate_schema(Proposal)
    ∧ lease_still_valid
    ∧ authorization_still_valid
    ∧ preconditions_still_hold
    ∧ effect_policy_allows
    → append authoritative transition

The Frontier should answer possibility, not preference. The allocator answers preference. The lease answers temporary authority. The execution-control boundary decides whether a proposed effect actually becomes real.

That separation prevents the Frontier from slowly accreting scheduler semantics until you're back to a DAG orchestrator.

The most important OSS analogue: Kueue + Drools, not an agent framework

This was the strongest result of the research round.

Drools gives you the conceptual implementation of a Frontier: facts enter working memory, conditions match, and multiple eligible activations coexist rather than forcing one next step.

Kueue then gives you what Drools doesn't: just because an activation is possible doesn't mean it should consume resources yet. Quota reservation and admission checks occur before admission, with explicit reasons and policies for preemption/fairness.

I would copy that division, not necessarily either codebase:

Drools-ish              Kueue-ish
facts                    eligible workload
  ↓                         ↓
matches                  quota/resource reservation
  ↓                         ↓
FRONTIER                 admission policies
                            ↓
                         ADMITTED SET
                            ↓
                         lease/execution

That's much closer to your missing abstraction than CrewAI/AutoGen/LangGraph-style orchestration.

Where I would revise your original table

Keep ISO 37000. It remains the right constitutional/top-level governance anchor.

Keep W3C ORG + OMG Commons, but add PROV-O and runtime authorization. Role/Post/Authorization is necessary, but insufficient once actual processes begin acting. Commons 1.3's new explicit authorization vocabulary makes your choice even stronger.

Keep MIT CISR, with one modification: assign risk × ambiguity to decisions/effects, not to “agents.” Their Frame → Act → Learn decomposition is useful precisely because different portions of one decision can have different human/AI allocations.

Keep CMMN + DMN. I'd now pair them conceptually with the Drools agenda and Kubernetes reconciliation loop.

Demote UAF one layer. Excellent for preserving enterprise relationships and views; too broad to be the operational kernel. Put BMM/BACM nearer the Meta-Harness domain model. OMG itself describes BACM as capability-centered.

Keep the contradictory MAS findings as a design requirement. OrgAgent reports benefits from explicit governance/execution/compliance hierarchy in its benchmarks, while the large self-organization study found strong models often benefit from much lighter scaffolding. That means topology should be compiled per task, not constitutionalized.

And the newest Fluid Structure, Rigid Record work lands almost exactly there: persistent authority/record structure, dynamically compiled operational worlds and task groups.

The architecture I would bet on

I'd now describe Meta-Harness as a constitutional reconciliation control plane:

PURPOSE / INTENT
ISO 37000 + BMM + BACM
        │
        ▼
WORLD / CASE

        │

        │
        ▼

        │
        └──────────────► reconcile again

The critical property is that no agent owns that loop.

Agents can propose candidates, estimate value, interpret ambiguous evidence, perform work, review work, and recommend reallocation. But the durable organizational truth—authority, admission, commitments, resource ownership, accepted effects, provenance—lives outside their conversational state.

That gets you out of both failure modes:

DAG/workflow trap: assumes you know one process/order in advance.

Corporate-agent trap: assumes organizational structure is equivalent to a communication topology between personalities.

Your Frontier becomes something closer to an organizational control surface over a continuously changing possibility set.

And I think that is the strongest architecture the current evidence supports. The 2026 literature is actually converging toward your “model, don't simulate” principle; it just hasn't yet produced a single mature OSS package that puts all of these pieces together.

## The missing primitive is not a scheduler

This is where I would make the plan more aggressive **and** more elegant.

Do not add a queue.

Do not add a daemon.

Do not add “parallel-agent orchestration.”

Add exactly one small runtime primitive:

```text
candidate-claim/v1
```

or, if you prefer the authority language:

```text
admission-lease/v1
```

A fresh session performs something equivalent to:

```text
claimNext(world, projection, existingClaims)
```

The algorithm is:

```text
read current World
→ derive eligible candidates
→ remove candidates conflicting with live claims
→ take highest-preference remaining candidate
→ atomically create claim(candidateId)
    ├─ success → execute it
    └─ collision → immediately try next candidate
```

That is distributed work stealing.

You don't need a manager agent.

You don't need a mutable queue.

You don't even need the chats to know about one another.

Ten fresh ChatGPT conversations can all receive the **same generic instruction**:

```text
Open repository X and execute the next available product scope.
```

The durable claim protocol makes them resolve to different work.

That is much more powerful than pre-assigning Chat A = dashboard, Chat B = cascade, etc., because pre-assignment reintroduces a planner/orchestrator.

## One more important correction: stop binding execution freshness to the entire WorldHead

The attached plan proposes binding `repo-decision/v4` to both:

```text
worldHeadDigest
allocationProjectionDigest
```

and then selecting one candidate.

That is correct for strict serial execution.

It is too coarse for parallel execution.

Suppose Dashboard and Cascade are independent:

```text
World H

Dashboard claim → starts
Cascade claim   → starts

Dashboard closes
World becomes H+1
```

If Cascade's authority says:

```text
worldHeadDigest must still equal H
```

then Dashboard's unrelated completion invalidates Cascade.

You have accidentally serialized at the **commit boundary** instead.

The elegant solution is MVCC-like scoped freshness.

Candidate C should retain:

```text
originWorldHeadDigest: H       # provenance

preconditionDigest: Pc         # actual freshness boundary
conflictKeys: [...]
dependencies: [...]
```

Then at effect admission/commit:

```text
origin H changed?
    → okay by itself

candidate-relevant facts changed?
    → reject/reconcile

candidate-relevant facts unchanged?
    → commit remains legal
```

So:

```text
WorldHead
```

answers **where this work came from**.

```text
preconditionDigest
```

answers **whether this work is still valid**.

That distinction is essential for parallelism.

That's exactly the shape you want.

## “Maximum parallelism” needs conflict structure

There is one subtle distinction worth locking down.

Simply letting every eligible candidate execute is unsafe.

You need to know whether candidates interfere.

The projection therefore needs a minimal conflict footprint, for example:

```text
Candidate A
  allowedPaths: ["dashboard/**"]
  conflictKeys: ["dashboard"]

Candidate B
  allowedPaths: ["cascade/**"]
  conflictKeys: ["cascade"]

Candidate C
  allowedPaths: ["shared/schema/**"]
  conflictKeys: ["schema"]

Candidate D
  allowedPaths: ["dashboard/**", "shared/schema/**"]
  conflictKeys: ["dashboard", "schema"]
```

Then an admissible wave may be:

```text
A + B + C
```

but not:

```text
A + D
```

The kernel does **not** need to understand what “dashboard” means.

It only proves compatibility.

This gives a clean abstraction:

```text

    What could legally run?

    Which work is most valuable?

    Which of those may safely coexist?

    Which fresh session owns each one now?
```

That's enough.

No CEO agents.

No meetings.

No scheduler lifecycle.

Those are very different invariants.

# But no: one SAW/code review will not make the architecture modular

This is the important answer.
