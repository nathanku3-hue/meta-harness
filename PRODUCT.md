# Meta-Harness product direction

## Version

product-direction-v2

## Endgame

One solo developer states the desired software result once. Meta-Harness turns that result into working code through sealed continuity, safe workspace selection, a read-only coding worker, exact validation, bounded repair, and concise product closure. The owner intervenes only for taste, scope expansion, credentials, protected access, publication, destructive action, or material risk.

## Target user

A solo developer/researcher shipping complex multi-module systems who needs AI coding throughput without losing product direction across interrupted rounds.

## Core user journey

```text
owner-authored product direction
→ high-level intent
→ planner decomposition
→ multiple Outcomes
→ automatic dispatch
→ exact validation
→ bounded repair
→ observable result
```

Phase-5 execution law:

```text
Planner proposes meaning.
Kernel grants exact capability.
Claim makes commitment durable.
Worker executes.
World learns.
```

The primary command is `meta-harness work`. Product direction is stated once in this file and must survive every session, repair, and resume unchanged until the owner edits this file.

## Taste — prefer

- One functional slice that creates newly observable product behavior.
- Immediate coding action from an accepted brief without reopening planning.
- Exact owner-authored direction bytes pinned into every work session.
- Fail closed when direction, path boundary, validation, or identity is ambiguous.
- Delete unconsumed active paths rather than preserve compatibility without a proven user need.
- Plain product language in normal output; evidence terms only in advanced surfaces.

## Taste — reject

- Reconstructing product philosophy from status files, audits, or defect lists each round.
- Init-generated or worker-authored taste, summaries, or philosophy templates.
- Silent direction drift, mixed old/new direction, or resume that ignores live PRODUCT.md.
- Governance gravity: dashboards, queues, daemons, swarms, or provider frameworks before a real slice proves need.
- Treating documentation, review, packaging, or evidence refresh as independent successor slices.
- Backward-compatibility aliases for retired session contracts.

## Non-negotiables

- PRODUCT.md is owner-authored only. Meta-Harness may read, hash, snapshot, and display drift; it must not generate, fill, summarize, relocate, or auto-overwrite it.
- Every active work session pins exact product-direction bytes and digest before the worker runs.
- Resume requires persisted content, persisted digest, and live PRODUCT.md bytes/digest to agree.
- The coding worker is read-only; the controller materializes validated changes and rejects any mutation of PRODUCT.md.
- Workers execute authorized reversible work without routine owner gates.
- Test success alone is not product success; shipping effect and user-visible capability matter.

## Shipping definition

For each coding result, terminal state is an observable repository change with controller-owned validation passed. Score claims require demonstrated product journeys, not implementation-only diffs. Publication, push, and external release remain explicit owner authority.

## Change rule

Only the owner may change this file. Engineering may propose amendments with evidence; the owner accepts or rejects by writing a new Version section and content. Future work sessions adopt the new version; in-flight sessions fail closed if this file changes mid-session.
