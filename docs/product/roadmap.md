# Meta-Harness Top-Level Roadmap

Intent authority: [Product Intent Anchor](product-intent.md)
Operating model: [Minimal Outcome Operating Model](minimal-outcome-operating-model.md)
Implementation checklist: [Minimal Outcome System Update Checklist](minimal-outcome-update-checklist.md)

## Endgame

One solo developer/researcher can use AI to ship ultra-complex, multi-module products with specialist knowledge applied directly to real product behavior, while minimizing elapsed time, human interruption, permanent process, and escaped defects.

The system must optimize completed Product Episodes, not plans, candidates, gates, scores, or process artifacts.

## Current frontier — close Meta-Harness 0.4

Preserve H3R2 as the exact release candidate. Do not mix the redesign below into H3R2.

Remaining product path:

1. confirm the exact H3R2 branch identity is durably available;
2. install the already-built exact tarball into one clean supported Node 20+ canary;
3. run one fresh-session terminal Product Episode;
4. perform one terminal Product/System/Release assessment;
5. tag and publish the same artifact without rebuild;
6. reconcile publication and close 0.4;
7. use one real repository canary before wider rollout.

No new H3R2 source work is justified unless the remaining real Episode exposes a concrete product defect.

## 0.5A — Minimal control loop and Git autopilot

### Product result

A user can start a fresh session with one lean role invocation, and Meta-Harness resumes the exact product outcome, creates a clean isolated worktree, executes the real Episode, and returns a compact result without a long prompt or routine approval waits.

### Scope

- root role router;
- PLAN, WORK, and AUDIT skills;
- compact product anchor;
- Slice Charter;
- Result Record;
- generated handover;
- clean-worktree Git autopilot;
- notify-first action policy;
- STOP after closure;
- deletion of automatic successor planning and score-first reporting.

### Acceptance

- dirty user checkout remains unchanged;
- correct base and default branch are detected;
- clean worktree, slice branch, focused commit, and configured branch push occur automatically;
- worker does not redesign the roadmap;
- auditor does not plan a successor;
- closed Eureka state returns STOP;
- Leningrad selects the complete real simulation;
- Quant selects a real prospective strategy Episode.

## 0.5B — Product/System/Release proof separation

### Product result

Every active slice proves a real user Episode before optional release ceremony, and diagnostics no longer receive universal product-candidate treatment.

### Scope

- Product Episode schema and Result Card;
- Product proof, System proof, and Release proof classification;
- artifact-sensitive completion law;
- affected-evidence reuse;
- one-repair budget;
- removal of evidence-only and lifecycle-fragment slices.

### Acceptance

- Leningrad cannot claim product completion before the complete declared simulation and report inspection;
- Quant cannot claim product completion before a prospective strategy Episode through reopen and explanation;
- a diagnostic closes with reproducibility, bounded scope, and decision usefulness;
- documentation projection does not create a second approval cycle.

## 0.5C — Decision-bound research

### Product result

External research changes one real implementation or product decision without expanding coding context or creating an open-ended survey.

### Scope

- conditional RESEARCH skill;
- decision question and stop condition;
- rejection-first primary-source citations;
- COPY/MODIFY/REJECT matrix;
- compact Research Decision Record;
- injection of only selected constraints, tests, and patterns into the Slice Charter.

### Acceptance

- rejected repositories lead with the specific rejection and citation;
- selected source states exact reuse and deliberate modification;
- worker does not receive the full research survey;
- research cannot create roadmap authority.

## 0.5D — Event-triggered retrospective

### Product result

Meta-Harness learns from expensive or surprising slices without adding a mandatory reflection round to normal work.

### Scope

- conditional RETROSPECT skill;
- triggers based on closure, abandonment, budget exhaustion, repeated failure/intervention, model change, or explicit request;
- KEEP/DELETE/SIMPLIFY/TEST/INVESTIGATE findings;
- non-authoritative improvement-candidate queue;
- generated handover separated from reflection.

### Acceptance

- normal successful slices do not run RETROSPECT;
- retrospective cannot reopen the product slice;
- a finding requires repeated failure or material irreversible risk before becoming active harness work.

## 0.6 — Harness diet and role-language rewrite

### Product result

The active system uses engineering problem-solving language and materially fewer always-on instructions, commands, templates, phases, and reports while preserving product, correctness, and safety outcomes.

### Scope

- adaptive engineering-reasoning skill;
- concise communication-style fingerprint;
- consolidation of scope, ship-fast, build/borrow, and decision-gate prose into role skills;
- demotion of phase choreography, expert packets, context scoring, lookback, and detailed worker reports to optional tools;
- deletion of obsolete backward-compatible process concepts.

### Acceptance

- planning separates observations, inferences, and unknowns;
- materially different options and real trade-offs are compared;
- cheapest discriminating experiment is selected;
- gate language appears only at real deterministic or irreversible boundaries;
- normal context and response size decrease without worse historical-scenario outcomes.

## 0.7 — Model-upgrade constraint challenge

### Product result

Meta-Harness can prove that stronger models no longer need specific scaffolding and delete it safely.

### Scope

Run historical holdout scenarios in three modes:

1. model plus repository only;
2. lean role skills plus charter;
3. full old harness.

Each retained constraint records origin, regression, last demonstrated value, and deletion condition.

### Acceptance

- delete a rule when model+repo or lean skills preserve the outcome;
- keep prose only when it changes repeatable reasoning;
- keep tests for mechanical correctness;
- keep hooks for deterministic invariants;
- keep sandbox or external controls for real blast radius;
- run after major model upgrades and at least quarterly.

## Later product roadmap

Only after the minimal operating system proves reduced time-to-Episode and human friction:

- repeated single-worker operation across real repositories;
- research-to-product conversion measured by changed behavior or acceptance;
- optional multi-agent fan-out when one worker cannot meet the outcome economically;
- learning and recommendation improvement measured on holdout decisions;
- broader rollout only from demonstrated repository demand.

## Explicitly rejected roadmap items

Do not open these without a real active-slice blocker:

- generic orchestration framework;
- universal workflow daemon or queue;
- mandatory multi-agent swarm;
- new context-scoring program;
- universal owner-approval workflow for reversible actions;
- broad hook framework for product decisions;
- compatibility layer for retired process concepts;
- automatic status-driven roadmap generation;
- evidence, documentation, review, package, or integration as standalone product phases.

## Success measures

- time to first real Product Episode;
- real Episode completion rate;
- decision utility;
- human interruption count;
- audit/repair rounds before reality;
- evidence reuse rate;
- escaped product defects;
- permanent complexity added or deleted;
- constraints removed after model upgrades;
- product work time versus process time.
