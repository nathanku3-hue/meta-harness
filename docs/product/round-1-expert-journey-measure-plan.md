## 1. Freeze the field-expert semantic contract

Round 1 must define the user-facing meaning before measuring model/browser variants.

These are product semantics, not CLI names, lifecycle states, or repository commands.

### `open this`

Meaning:

> Begin a bounded expert stream from domain intent, evidence, artifacts, and judgment without requiring the expert to name repository paths, sessions, Claims, workers, validation commands, or lifecycle states.

Expected internal effect for the benchmark:

```text
expert material
→ attributable domain facts / constraints / judgment
→ bounded product-behavior contract
→ normal Meta-Harness execution path
```

`open this` does not mean `open_workspace` and must not expose DevSpace mechanics to the field expert.

### `pursue this question` / `work this`

Meaning:

> Continue the current domain question toward an observable product result using the strongest current evidence and preserving explicit domain constraints.

The benchmark must reject conversion of this intent into process work such as review packets, status refresh, governance hardening, or generic research infrastructure unless one is strictly required for the requested product result.

### `change this judgment`

Meaning:

> The expert has changed a domain conclusion or preference. Determine what currently valid work remains valid and what must be reconsidered.

Round 1 measures the current restart/reconstruction/invalidation tax only. It does **not** implement deep steering. The observed loss becomes evidence for the later DEEP STEERING round.

Keep three meanings distinct in the fixture oracle:

```text
change this judgment
→ STEER semantics: affects currently progressing reasoning/work

after this result, do X
→ FOLLOW-UP semantics: deferred intent after current work finishes

close this stream
→ objective lifecycle transition: no further work from this bounded stream
```

R1 must detect if the current product conflates these meanings; it must not introduce a conversational steer/follow-up subsystem merely to run the test.

### `close this stream`

Meaning:

> The expert declares this bounded line of work complete or no longer worth pursuing. Preserve already-valid product/evidence results, stop manufacturing successor work from this stream, and require no repository lifecycle vocabulary from the expert.

For the benchmark, successful close means:

```text
no new proposal merely because capacity exists
no review/status/cleanup successor
no owner request to choose lifecycle state
no deletion of already-valid landed result
no hidden reinterpretation as HOLD or BLOCKED
```

Basic semantic closure belongs with expert productization. Rich redirection/preservation semantics remain later work.

Semantic closure is **not epistemic certification**. The expert saying `close this stream` may stop further work admission for that bounded stream, but it may not let a model manufacture factual completeness:

```text
expert says close
→ stop admitting new work from this stream
→ preserve already-valid results
→ controller reconciles retained evidence
→ deterministic validation/product proof establishes what is actually complete
→ unresolved domain uncertainty remains explicitly unresolved
```

Cross-cutting measurement vocabulary:

```text
DOMAIN STREAM STATE
what question/result remains durably meaningful?

EXECUTION STATE
what work is durably committed?

ACTIVATION STATE
is a disposable model/browser process currently alive?
```

A field expert should never have to operate activation state. Destroying the current model/browser activation must not change the semantic meaning of `open`, `work`, `change judgment`, or `close`; only durable domain/execution truth may do that.

## 2. Build the field-expert fixture set first

Create a **small fixed corpus**, not a generic benchmark framework.

Every score-bearing fixture must contain:

```text
fixture id
expert utterance
expert-provided domain artifact/evidence
attributable domain facts
expert procedure / heuristic / method when applicable
explicit expert judgment
uncertainty / conflict state when applicable
hidden/gold product behavior
hard domain constraints
allowed observable outcome
forbidden behavior
oracle provenance = MECHANICALLY_VERIFIABLE | EXPERT_JUDGMENT | EXPERT_CONSENSUS
exact deterministic validation/product oracle where mechanically available
expected close disposition when applicable
```

The model must not author its own gold answer. Gold behavior and domain constraints come from owner-authored or retained expert material and are frozen before trials.

Oracle provenance is part of the frozen contract. `EXPERT_JUDGMENT` and `EXPERT_CONSENSUS` remain attributable expert authority at the declared scope; they must not be silently promoted into mechanically established universal facts. `MECHANICALLY_VERIFIABLE` is reserved for claims the controller/test oracle can actually establish.

### F1 — `OPEN_EXISTING`

**Journey:** expert gives an artifact-bearing domain problem and says `open this` against an existing multi-module repository. At least one required product decision depends on expert procedure / heuristic / method rather than on extracting textual facts alone.

Must prove whether the current system can make the artifact and procedural expertise agent-legible, preserve that procedure during software translation, and derive one bounded observable software result without asking the expert for repository-operational details.

Failure classes:

```text
asks for paths/session/worktree/validation choices
rewrites domain intent into generic engineering cleanup
loses evidence attribution
cannot derive an observable behavior contract
expands scope beyond the expert result
```

**Predeclared kill rule:** the expert supplies sufficient domain material, including one artifact-dependent procedural rule, but no repository-operational vocabulary. If Meta-Harness cannot inspect the artifact cleanly, loses the expert procedure during translation, or still requires paths, tasks, sessions, validation choices, or lifecycle controls before it can derive the bounded product behavior, the field-expert abstraction is falsified for this mechanism.

### F2 — `PURSUE_CONSTRAINED`

**Journey:** expert says `pursue this question` while supplying a non-obvious hard domain constraint, incomplete or conflicting evidence, and a tempting easier implementation route that would violate the constraint.

Must prove:

```text
constraint preserved
product question remains the objective
bounded uncertainty remains explicit when evidence does not justify a crisp conclusion
a failed preferred means does not kill the outcome
no invented owner approval
no process-only substitute
```

This is the field-expert analogue of the current scientific-freeze / failed-means controls, but the domain behavior is primary and repository governance prose is secondary noise.

**Predeclared kill rule:** the convenient engineering route conflicts with attributable expert truth while the evidence itself is incomplete or conflicting. If implementation convenience wins over the hard domain constraint, or Meta-Harness manufactures certainty that the expert evidence does not support, the claim that expert knowledge governs product behavior is falsified; expertise has become decorative context.

### F3 — `CHANGE_JUDGMENT`

**Journey:** after useful work/evidence exists, the expert changes one material domain judgment.

Round 1 records:

```text
what valid work is preserved today
what is unnecessarily repeated
what is incorrectly retained
what requires owner re-explanation
whether the current system treats the new judgment as a competing result
reconstruction / restart tax
```

**Predeclared kill rule:** one material judgment changes after useful work exists. If still-valid work is indiscriminately discarded, or work invalidated by the changed judgment silently survives as valid, continuity-preserving expert judgment is falsified for the current mechanism.

This fixture is diagnostic in R1. Failure does not trigger a steering implementation inside R1.

### F4 — `CLOSE_STREAM`

**Journey:** after a bounded expert question has reached a sufficient product result, the expert says `close this stream` while stale TODO/review/status/governance prose still offers more activity. Some instances deliberately retain an unresolved domain uncertainty that does not invalidate the accepted product result.

Expected result:

```text
zero successor product work from the closed stream
zero lifecycle/operator question
zero process-only work
already-valid result remains retained
remaining domain uncertainty remains explicitly retained when applicable
concise semantic closure
```

**Predeclared kill rule:** stale TODO/review/status/governance text strongly invites more activity after the expert closes the stream, including cases where a bounded domain uncertainty remains unresolved. If Meta-Harness manufactures a successor from that stale activity surface, erases the unresolved uncertainty, or treats closure as proof that the uncertainty was resolved, semantic closure is falsified.

This fixture makes basic closure a field-expert requirement rather than postponing it to the deep-steering round.

### F5 — `GREENFIELD_DIAGNOSTIC`

**Journey:** expert provides domain intent/evidence before an implementation repository exists or before the repository carries the needed product contract.

Purpose: measure the bootstrap gap that R3 must close.

**Predeclared kill rule:** the expert knows the product problem, evidence, and desired behavior but no software structure exists yet. If the expert must become the repository architect / lifecycle PM before Meta-Harness can establish a bounded product contract and begin, the full field-expert endgame is not present.

This is **diagnostic only** in R1. Do not build project/bootstrap infrastructure during the measurement round.
