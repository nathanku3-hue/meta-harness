# Meta-Harness 0.4 Product Requirements

## Problem

Repository automation can prove hashes, commands, reviews, and custody while still choosing work that does not improve the user’s next outcome. Status and lifecycle machinery can become the work.

## Requirement

Meta-Harness 0.4 must make the owner-authorized product result the planner’s first decision surface.

The installed planner shall:

1. reconcile locked intent and owner authority before status;
2. identify whether the complete user journey has run;
3. select the nearest executable action that produces the observable result;
4. permit at most one pre-execution audit/repair round;
5. block only demonstrated journey prevention, material conclusion invalidation, credible irreversible loss, or supported-platform unusability;
6. reuse passed evidence when its dependency surface is unchanged;
7. keep implementation through closure inside one functional slice;
8. expose the user journey and result as the first five worker-report fields;
9. ship DELIVERY authority only;
10. stop with `NO_BUILD` and `USE_PRODUCT` after shipped or value-confirmed completion unless explicit owner scope change or a complete observed supported-use defect warrant exists.

## Acceptance fixtures

- Leningrad: run the complete journey now; optional reviewer findings do not block.
- Quant: preserve unaffected passed product evidence and rerun only the changed gate.
- Eureka: a fresh session derives terminal `NO_BUILD` / `USE_PRODUCT` from scenario and authority, not caller booleans.
- Truth conflict: stale status cannot create a slice against higher authority.
- Continuation: only explicit owner scope change or a complete supported-use defect warrant permits build recommendation; no successor activation is claimed.

## Non-goals

No key-management service, vault abstraction, workflow framework, multi-agent expansion, broad deployment automation, compatibility authority, or blanket installation into existing repositories.
